# Практикум по направлениям исследования

[Обзор добавленных вопросов](research-expansion-review.md) · [Документация](README.md)

Шесть упражнений дополняют q741–q840. Это самостоятельная практика с критериями самопроверки, без обязательного поля «мои размышления». Данные синтетические; упражнения выполняются локально. Они не включены в число вопросов банка и не выдают автоматическую оценку практических навыков.

## 1. Код-ревью и исправление

Контракт: поле `approved` должно быть булевым значением JSON. Недопустимый тип — ошибка валидации, а не согласие и не отказ по умолчанию.

```python
def parse_approval(payload):
    return bool(payload.get("approved", False))
```

Найдите нарушение контракта, исправьте функцию и напишите проверки для `true`, `false`, строки `"false"`, числа `0`, `null` и отсутствующего поля. В Python проверяйте именно булев тип, не подменяя его общей проверкой чисел. В объяснении разделите проблему преобразования типов и задачу серверной авторизации.

**Самопроверка:** принимаются только два булевых значения; остальные четыре случая отклоняются с ошибкой. Исправление не должно превращаться в `return False` для любого ввода. Покажите один провал старой реализации и прохождение исправленной.

Связанные вопросы: q765–q766, q801–q810.

## 2. Python и запрос к журналам

Вход: [events.jsonl](research-practice/events.jsonl). Напишите скрипт, который читает файл построчно, разбирает время с часовым поясом и выводит отчёт по полуоткрытому окну `[2026-10-10T10:00:00Z, 2026-10-10T10:01:00Z)`.

Требования:

- Повтор одного `event_id` учитывать один раз; сохранять счётчик дублей.
- Строку с неверной датой учитывать как ошибку входа, продолжать обработку остальных.
- `outcome` может быть `failure`, `success` или отсутствовать. Отсутствие не равно успеху.
- Для окна отдельно считать события `failure`, разных пользователей с такими событиями и записи с неизвестным результатом.
- Не включать запись точно на правой границе. Нормализовать смещения, не удалять их текстовой заменой.

**Самопроверка:** 1 повтор доставки, 1 неверная дата, 1 запись за окном. В окне 3 неудачи, 2 разных пользователя с неудачами и 1 неизвестный результат. Итог не меняется при перестановке строк.

Дополнительно загрузите валидные записи в локальную SQLite-таблицу, сохранив время в UTC, и получите те же числа SQL-запросом. Объясните, почему `COUNT(*)` отличается от `COUNT(DISTINCT user_id)` и на каком этапе убираются дубли.

Связанные вопросы: q771–q780, q789.

## 3. Разбор PCAP

Откройте [training-http.pcap](research-practice/training-http.pcap) в Wireshark. Это синтетический полный захват одного HTTP-обмена с документационными IP-адресами, без реальных секретов. Файл можно исследовать без подключения к сети.

Определите клиент и сервер, порты, число TCP-соединений, HTTP-метод, путь и ответ. Найдите повторную передачу. Сравните сумму полезной нагрузки пакетов клиента с количеством уникальных байтов восстановленного запроса. Обоснуйте, почему повторная передача не означает вторую прикладную операцию.

**Самопроверка:** клиент `192.0.2.10:51000`, сервер `198.51.100.20:80`; одно соединение; запрос `GET /health`, ответ `200 OK`, тело `OK`. В захвате 9 пакетов, одна повторная передача первого фрагмента запроса. Точные длины для проверки приведены в [capture-facts.json](research-practice/capture-facts.json). Из этого захвата нельзя делать вывод о содержимом других соединений или об отсутствии атак в системе.

Связанные вопросы: q795–q800; прежние q322 и q327 остаются отдельными задачами.

## 4. Матрица авторизации

Политика учебного сервиса: редактор читает и меняет собственный черновик; собственный опубликованный документ только читает. Чужие документы недоступны. Наблюдатель читает только собственный опубликованный документ. Неаутентифицированному клиенту доступ запрещён.

| Субъект | Объект | Действие | Ожидается |
|---|---|---|---|
| Редактор A | Черновик A | Читать | Разрешить |
| Редактор A | Черновик A | Изменить | Разрешить |
| Редактор A | Опубликованный A | Читать | Разрешить |
| Редактор A | Опубликованный A | Изменить | Запретить |
| Редактор A | Черновик B | Читать | Запретить |
| Редактор A | Черновик B | Изменить | Запретить |
| Наблюдатель A | Опубликованный A | Читать | Разрешить |
| Наблюдатель A | Черновик A | Читать | Запретить |
| Анонимный клиент | Опубликованный A | Читать | Запретить |

Реализуйте локальную функцию решения и тесты по таблице. Для изменения используйте копию учебного хранилища; при отказе проверьте отсутствие изменения. Добавьте смену статуса черновика и повторный запрос, чтобы обнаружить неправильный кеш решения.

**Самопроверка:** совпадают все девять решений; отказ не меняет объект; успешное чтение A не открывает доступ к B; публикация прекращает разрешение на изменение. HTTP-код без проверки состояния недостаточен.

Связанные вопросы: q816, q819–q820, q822–q823.

## 5. Почтовые заголовки

Ниже нормализованные результаты **собственного доверенного** принимающего шлюза, а не заголовок от отправителя. Для упражнения подписи уже проверены. Сопоставьте домены с `From: user@company.example`; режим alignment строгий, других ошибок нет.

| Письмо | SPF | DKIM |
|---|---|---|
| A | pass, MAIL FROM `mailer.example` | pass, d=`company.example` |
| B | pass, MAIL FROM `mailer.example` | pass, d=`other.example` |
| C | fail, MAIL FROM `company.example` | pass, d=`company.example` |

Укажите результат DMARC и объясните, что он говорит о вредоносности вложения и личности автора. Затем измените доверенность источника: эти результаты оказались произвольным входящим `Authentication-Results`. Какие проверки пришлось бы выполнить на своём шлюзе?

**Самопроверка:** A и C проходят через согласованный DKIM; B не проходит. DMARC не доказывает безопасность содержимого или личность человека. Произвольную входящую строку результатов нельзя принимать за собственную проверку. Используется [RFC 9989](https://www.rfc-editor.org/rfc/rfc9989.html), заменивший RFC 7489 и RFC 9091 в мае 2026 года.

Связанные вопросы: q741–q750.

## 6. Устный разбор архитектуры и собственного вклада

За 15 минут спроектируйте сервис экспорта документов нескольких организаций: браузер → API → очередь → worker → хранилище → временная ссылка. Права могут отозвать, пока задание находится в очереди. По условию они должны быть действительны при выполнении. Разные организации не должны получать данные друг друга.

Представьте потоки и границы доверия; место проверки прав и отзыва; область полномочий worker; условия жизни ссылки; пределы очереди; журналирование без секретов. Назовите три негативных теста, способ обнаружения отказа и безопасное восстановление. Для руководителя добавьте владельцев рисков, критерии внедрения безопасного шаблона и метрику возраста незакрытых проблем.

**Критерии самопроверки:** каждое защитное решение связано с угрозой и тестом; учтены асинхронность, отзыв, изоляция клиентов и перегрузка; есть сценарий отказа; назван остаточный риск. Один список названий инструментов не достаточен.

Для рассказа о своём проекте используйте: **задача → мой вклад → вклад команды → доказательство результата → ограничения**. Учебную работу называйте учебной, неизвестные результаты не приписывайте себе. Коммерческий опыт для этого упражнения не требуется.

Связанные вопросы: q821–q840. Это упражнение не заменяет полный практический стенд AD, разработку продвинутых эксплуатационных сценариев или оценку опыта Lead/Staff.
